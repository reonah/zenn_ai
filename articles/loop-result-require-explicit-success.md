手元の Mac では、launchd から Claude Code や Codex を定期実行する loop を何本も動かしている。各 loop は CLI が書き出す結果 JSON を読んで成否を決め、daily note に記録し、成功した回だけ「どこまで処理したか」の到達点を進める。

この成否判定には前史がある。claude は認証失効のとき、exit code 0 のまま結果 JSON の `is_error: true` だけで失敗を伝えてくることがある。それに気づいて、exit code と `is_error` の両方を見る判定関数 `run_failed` を共通ライブラリに置いた。以後、認証失効もターン上限も失敗として記録されるようになった。

2026-11-01、この共通処理を改めてレビューした。確認した指摘は 4 件で、うち 1 件はその `run_failed` 自身にあった。

## 失敗の印が無ければ成功だった

修正前の `run_failed` はこうなっていた。第 1 引数が結果 JSON のパス、第 2 引数が CLI の exit code である。

```bash
run_failed() {
  [ "${2:-0}" -eq 0 ] || return 0
  [ "$(jq -r 'if .is_error == true then "1" else "0" end' "$1" 2>/dev/null)" = "1" ]
}
```

exit code が非 0 なら失敗。0 なら `is_error` が `true` かどうかを見る。読み手の想定は「claude が正しい形の JSON を書いた」場合に限られていた。

その想定から外れた入力を 3 つ、一時ディレクトリで渡してみた。空ファイル、`{broken` という壊れた JSON、空オブジェクト `{}` である。3 つとも成功と判定された。空ファイルでは jq が何も出力しない。壊れた JSON では jq がエラーで終わり、そのエラーは `2>/dev/null` に消える。`{}` では `.is_error` が null なので `"0"` が返る。どの経路でも比較の右辺 `"1"` に一致せず、関数は「失敗ではない」を返す。

影響が具体的なのは、Databricks のリリースノートを日次で拾う loop だった。成功側の分岐で、到達点のファイルに当日の日付を書く。

```bash
if run_failed "$RUN_LOG" "$STATUS"; then
  # state は更新しない: 次回実行が今回の未カバー分を含めて拾い直す
  ...
else
  append_note "$(jq -r '.result' "$RUN_LOG")"
  ...
  echo "$TODAY" > "$STATE_FILE"
fi
```

空の結果や必須項目の欠けた結果が exit 0 で返ると、処理した証拠の無い期間が次回の対象から外れる。壊れた JSON の場合は後続の jq も失敗するため、日付の更新まで進むかどうかは結果の形しだいになる。

既存のテストは 43 項目すべて通っていた。並んでいたのは認証失効、ターン上限、API の一時過負荷といった、実際に遭遇した失敗の形である。既知の失敗を 1 つずつ登録していく作りなので、まだ見ていない壊れ方はテストにも判定にも入っていなかった。

## 成功の条件を列挙して、満たさなければ失敗にする

修正後はこうした。

```bash
run_failed() {
  [ "${2:-0}" -eq 0 ] || return 0
  ! jq -e -s '
    length == 1 and (.[0] | type == "object"
      and .is_error == false and .subtype == "success"
      and (.result | type == "string" and test("\\S")))
  ' "$1" > /dev/null 2>&1
}
```

失敗の印を探すのをやめ、成功と認める条件を書いた。結果は 1 個のオブジェクトであること。`is_error` が明示的に `false` であること (欠落は `false` とみなさない)。`subtype` が `"success"` であること。`result` が空白以外の文字を含む文字列であること。どれか 1 つでも欠ければ失敗になる。

`-s` (slurp) は入力全体を配列に読み込む。空ファイルは `[]` になり、`length == 1` で落ちる。結果オブジェクトが 2 個連なった出力も同じ条件で落ちる。壊れた JSON では jq 自体が非 0 で終わり、`!` で反転して失敗側に入る。条件式が偽のときに jq を非 0 で終わらせるのが `-e` である。

修正前の版に対して、追加したテストを先に流した。落ちたのは次の 9 件である。

- exit 0 でも空結果は失敗
- 不正 JSON は失敗
- 必須項目の欠落は失敗
- 成功フラグの欠落は失敗
- 成功 subtype の欠落は失敗
- 空白だけの最終応答は失敗
- 矛盾する subtype は失敗
- 複数の結果オブジェクトは失敗
- 配列は結果オブジェクトでない

既存の失敗ケースはこの時点でも全部通っている。古い判定は、知っている失敗を正しく拾えていた。問題は、知らない形の結果を成功の側に流していたことにある。

## 失敗と記録したのに exit 0 で終わる

2 件目は loop 本体の末尾にあった。`run_failed` が真になると、loop は daily note に失敗を書く。リリースノートの loop は macOS の通知も出す。ところが exit code 0 と `is_error: true` の組み合わせでは、`STATUS` 変数は 0 のまま最後の `exit "$STATUS"` に届く。

レビューでこの分岐だけを隔離して流すと、失敗側に入ったうえで終了コードは 0 だった。launchctl の終了値からは失敗が見えない。ハーネス監査を起動する trigger も正常終了とみなし、件数の基準線を先へ進める。daily note には失敗が残るため、記録が丸ごと消えるわけではない。とはいえ、人間向けの記録と機械向けの終了値が別の成否を語っていた。

修正は各 loop の失敗分岐に 1 行を足すだけで済んだ。

```bash
if run_failed "$RUN_LOG" "$STATUS"; then
  [ "$STATUS" -ne 0 ] || STATUS=1
```

元の exit code が非 0 ならその値を残し、0 なら 1 に変える。対象はハーネス監査、リリースノート、ブログ草稿、vault レビューの 4 本である。結果処理の部分を本物のスクリプトから切り出して流し、成功・失敗・空結果の 3 通りを 4 本それぞれで確かめた。

## SIGTERM で親だけが止まる

3 件目は Codex の実行ラッパー (Python) にあった。ラッパーは Codex を `start_new_session=True` で別のセッションに起動する。時間切れや一時停止ファイルを検知したときは、`os.killpg` でプロセスグループごと止める。この経路は正しく動いていた。

抜けていたのは、ラッパー自身が SIGTERM を受けた場合である。シグナルを捕まえる処理が無く、ラッパーはそのまま死ぬ。子は別セッションにいるので、巻き添えにならずに動き続ける。30 秒眠るだけの偽の Codex を起動してラッパーに SIGTERM を送ると、ラッパーは終了し、子は生きていた。正規化した結果 JSON も書かれなかった。親が止まっても、子が投稿などの操作を続けうる状態である。

Claude 側のラッパーには、同じ問題を扱う停止処理が既にあった。

```python
def terminate_group(process):
    signal_group(process, signal.SIGTERM)
    try:
        process.wait(timeout=2)
    except subprocess.TimeoutExpired:
        pass
    # The leader can exit while a descendant ignores SIGTERM.
    signal_group(process, signal.SIGKILL)
    process.wait()
```

修正では Codex ラッパーがこの関数を読み込んで使う。SIGTERM と SIGINT を受けたら例外を投げて読み取りループを抜ける。`finally` 節では、両シグナルをいったん無視に切り替えてから `terminate_group` を呼び、最後に元のハンドラへ戻す。中断の理由は結果 JSON に書く。

Codex 専用の停止処理を書き足す案もあった。同じ中断条件に対して実装が 2 つになり、片方だけ直る差が増えるため採らなかった。

テストでも 1 度つまずいた。子孫の生存を `ps` と Unix ソケットで確かめる最初の版は、sandbox で許可されずに動かなかった。これはラッパーの不具合とは別の失敗である。代わりに FIFO を握り続ける子孫を用意し、修正前は結果 JSON が欠落すること、修正後は子孫が終了することを確かめた。

## 2 本のログを 1 つの数で数えない

4 件目は監査の trigger である。ユーザの訂正を記録する correction-log の行数が閾値ぶん増えると、定期監査を待たずにハーネス監査を前倒しで起動する。監視していたのは `~/.claude/logs/correction-log.jsonl` だけだった。Codex の訂正は `~/.codex/logs/correction-log.jsonl` に書かれるため、Codex でいくら訂正が溜まっても前倒しは起きない。週 2 回の定期監査は Codex のログも読むので、訂正そのものは後で回収される。

修正では両方のログを監視し、前回の行数をログごとに別ファイルへ保存する。増分はログごとに計算してから合算し、合計が閾値以上なら起動する。

到達点を 1 つの合計値で持つ案は採らなかった。ログの作り直しで行数が減ったとき、基準線を合わせ直す処理がある。合計値しか無いと、片方のログが縮んだだけで、もう片方の未処理の増分まで基準線の下に消える。ログ別に持てば、縮んだログの基準線だけを合わせ直せる。あわせて、存在していたログが一時的に見えないときは到達点を戻さず、loop が失敗したときは到達点を進めない形にした。

修正前の trigger に対して、追加したケースは 15 件中 7 件が落ちた。「Claude1件とCodex2件を合算する」「Codexログ縮小でもClaude未処理3件は失わない」「既存Claudeカーソルの未処理増分を引き継ぐ」などである。

## 直したあとに確かめたこと

修正は 1 つのコミットにまとめた。対象の回帰テストは 52 項目、trigger は 15 項目、Codex ラッパーは 19 項目が通った。push 対象のコミットを隔離環境で検証する pre-push の全検証も通っている。監査 trigger は launchd に登録し直し、2 本のログの監視を確認した。一方で、実サービスへの投稿を伴う本番経路では動かしていない。

4 件のうち 3 件は、失敗を拾う仕組みが既にあるのに、拾えない形の結果がそのまま正常系に流れていた。判定関数は認証失効を拾い、loop は失敗を daily note に書き、ラッパーは時間切れで子を止めていた。それでも、空の JSON、終了値、外から届くシグナルは、どの仕組みにも登録されていなかった。成功の条件を先に書き、満たさないものを全部失敗に倒したことで、次に知らない壊れ方が来ても到達点は進まない。
