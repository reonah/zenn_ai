9 月 9 日、Claude Code のセッションが開始直後に何トークン読み込んでいるかを測る hook を入れた。初回の計測結果に、skill 一覧の内訳として「54 個」と出た。

私の dotfiles には自作の skill が 145 個ある。54 という数字は、plugin と組み込みの skill だけを数えるとぴったり合う。つまり自作 skill は 1 つも一覧に載っていなかった。試しに `Skill` ツールから自作 skill を呼ぶと `Unknown skill` が返る。hook も同じ経路で読まれるので、dotfiles で管理している hook (レビュー依頼を skill に振り分ける router、破壊的コマンドのガード、skill の起動ログ) も全部止まっていることになる。

では、いつから止まっていたのか。答えを先に書くと 1 か月前で、その 1 か月のあいだ誰も (私も、無人で回っているループも) 気づかなかった。

## 常駐費を測ろうとしていた

きっかけは別の話だった。Claude Code は CLAUDE.md、rules、memory、skill の一覧、MCP の説明を、会話が始まる前にコンテキストへ載せる。これらは作業の副産物として増える一方で、減らすのは独立した仕事になるので、放置すると増える側が勝つ。そこで「減らす仕組みより先に、増えたことに気づく仕組み」として、セッション開始直後の最初の応答が読み込んだ入力トークン数を毎回記録することにした。この記事ではこの値を常駐費と呼ぶ。

初回の計測はこうだった。

| 項目 | 値 |
|---|---|
| 実測トークン (最初の応答の入力) | 55,071 |
| 起動時に添付された文字数の合計 | 152,493 |
| うち組み込みツール定義 | 110,221 |
| うち skill 一覧 | 24,218 (54 skill) |
| うち常時ロードの rules | 5,876 |
| うち CLAUDE.md | 3,145 |
| うち memory の索引 | 2,767 |

常駐費そのものの話としては、削れる層で一番大きいのは skill 一覧で、組み込みツール定義は触れない層、という結論になる。ただ、この表を作っていて目に留まったのは 54 の方だった。

## headless で切り分ける

対話セッションでは条件を変えづらいので、`claude -p` で 1 ターンだけ走らせ、skill の数と hook の発火を条件別に見た。

| 起動条件 | skill 数 | 自作 skill | `~/.claude/settings.json` の hook |
|---|---|---|---|
| フラグなし (cwd 任意) | 196 | 載る | 動く |
| `--setting-sources project,local`、cwd = ホーム | 49 | 載らない | 動く |
| `--setting-sources project,local`、cwd = リポジトリ | 13 | 載らない | 動かない |
| 上に加えて `--setting-sources user,project,local` を後置 | 196 | 載る | 動く |

`--setting-sources` は読み込む設定の出どころを `user`、`project`、`local` から選ぶフラグで、`user` を外すと `~/.claude/settings.json` と `~/.claude/skills` が読み込み対象から消える。dotfiles の hook も自作 skill もここにある。

私は `claude` を、シェルの alias で wrapper コマンド経由で起動している。この wrapper が既定で `--setting-sources project,local` を付けていた。目的は古い `apiKeyHelper` の設定が混入するのを防ぐことで、意図としては分かる。ただ私の `~/.claude/settings.json` に `apiKeyHelper` は無く、代わりに hook と skill がまとめて消えていた。表の最後の行が示すとおり、同じフラグを後ろにもう一度置けば後の方が勝つので、対処自体は 1 行で済む。

## なぜ 1 か月気づかなかったか

wrapper 経由の起動に切り替えたのは 8 月 10 日だった。9 月 9 日まで、対話セッションでも launchd の無人ループでも、hook と自作 skill は効いていないままだった。

気づかなかった理由は表の 2 行目にある。ホームディレクトリで起動すると、`~/.claude/settings.json` が user 設定ではなく project 設定として読まれる。ファイルの場所が同じだからだ。だから雑にホームで `claude` を打ったときには hook が動き、リポジトリの中で開いたときだけ動かない。挙動が場所で変わるので、「たまに効かない気がする」以上の輪郭にならなかった。

もう 1 つ、Claude Code は skill が無くてもエラーで止まらない。`Skill` ツールが `Unknown skill` を返しても、モデルは skill 無しで作業を続ける。無人ループはこれが致命的で、note の記事を書くループ、ブックマークを収集するループ、この記事を書いているブログのループが、それぞれ主目的の skill に届かないまま「完了」を報告し続けていた。後から transcript を数えると、8 月 20 日以降の `Unknown skill` は 15 件で、そのうち 7 件がこの 3 本の無人ループだった。

証拠は最初からログにあった。skill の起動ログを見ると、8 月 11 日以降に自作 skill の起動が 1 件も無い。ただし、この起動ログを書いているのも dotfiles の hook である。hook が止まった状態で起動ログが空なのは、skill が使われなかったからではなく、記録する側が居なかったからで、ログを眺めているだけではこの 2 つを区別できない。

被害はもう 1 つ後から出た。skill の棚卸しでは、導入から 90 日を超えて起動 0 回のものを削除候補にしている。8 月 10 日から 9 月 9 日までの計測が無効になったため、52 件あった削除候補は、有効な計測が 5 日分しか無いという理由で次回に持ち越しになった。

## 直したこと、直していないこと

launchd からの起動は 8 箇所あった (無人ループ 7 本と、CLI 認証の生存点検 1 本)。全部に `--setting-sources user,project,local` を明示した。それと、起動行を grep して継続行の中にこのフラグがあるかを見る回帰テストを足した。起動箇所が 8 件未満しか見つからなかったら、起動の書き方が変わってテストが取り逃していると判断して落ちるようにしてある。

対話セッションの alias は `~/.zshrc` にあって dotfiles の管理外なので、ここは自分への依頼として daily note に残した。

未解決事項が 1 つある。9 月 14 日の時点で alias はまだ直していない。ところが 9 月 13 日の対話セッションでは、alias が同じままなのに user スコープの hook と skill が読まれていて、`Unknown skill` も出ていなかった。wrapper 側の既定が変わったのか、別の要因があるのかは切り分けていない。alias の修正が今も必要なのかは、確認中というのが正直なところだ。

## 設定の存在ではなく、読まれた結果を見る

効いていなかった期間は 8 月 10 日から 9 月 9 日までの 1 か月だった。見つけたのは hook でも監視でもなく、別の目的で入れた計測の内訳にあった 1 行である。

設定ファイルがそこにあることと、そのセッションで実際に読まれたことは別の話で、Claude Code は後者をエラーとしては教えてくれない。今回それを教えてくれたのは skill 一覧の件数という副産物だった。常駐費の記録には skill の件数が毎回残るようになったので、次に同じことが起きても、1 か月後ではなく次の監査で数字が減った時点で分かる。
