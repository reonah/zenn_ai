dbt の増分モデル (`materialized='incremental'`) の結果は、その回の入力だけでなく、前回までの実行で残ったテーブルにも左右される。遅れて届いた行や同じ入力の再実行が重なると、全件を作り直した結果とずれることがある。

そこで、合成した入力を決めた順序で流し、増分側の結果と全件再計算の結果を毎回比べる小さな CLI (`dbt-incremental-check`) を作った。2026-10-02 に Databricks の Serverless Starter Warehouse で、dbt Core / dbt-databricks 1.11.8 を使って実機検証した。

## 1 回の実行を見るテストでは足りなかった

dbt には unit test があり、増分モデルも対象にできる ([dbt unit tests の増分モデルの検証範囲](https://docs.getdbt.com/docs/build/unit-tests#unit-testing-incremental-models))。`is_incremental()` を真にして、既存テーブル `this` の中身を入力として与えられる。ただし検証できるのは、その 1 回の実行で生成される行だ。MERGE を終えたあとのテーブル全体の状態は、unit test の YAML では同じ形で書けない。

知りたかったのは「初回、遅延到着、再実行と続けたあとに、テーブルの中身が全件再計算と一致しているか」だった。比較の正解には、同じ時点の入力から `--full-refresh` 相当で作り直した結果を使う。業務上の正解ではなく、全件再計算との一致を仕様とするモデルに限った比較になる。

## step は差分ではなくスナップショットにした

シナリオは step の列で、各 step は名前、時計 (`clock`)、ソース表の行を持つ。step の行は「今回追加された行」ではなく「その時点のソース表全体」と定義した。

同じ入力の再実行は、前の step と同じ行を並べるだけで表せる。遅延到着は、前の step の行に古い時刻の行を加えて表す。CLI は step ごとにソース表を丸ごと置き換え、増分側では同じ Delta テーブルを MERGE で更新し続ける。比較側は同じ SQL で毎回全件再計算する。

付属の例は次のシナリオだ。2 番目の step で、初回より古い `event_time` を持つ id=2 が届く。3 番目は同じ入力での再実行になる。

```json
{
  "oracle": "full_refresh",
  "columns": {"id": "BIGINT", "event_time": "TIMESTAMP", "amount": "BIGINT"},
  "unique_key": ["id"],
  "steps": [
    {"name": "initial", "clock": "2026-01-03T00:00:00", "rows": [
      {"id": 1, "event_time": "2026-01-02T00:00:00", "amount": 10}
    ]},
    {"name": "late_arrival", "clock": "2026-01-04T00:00:00", "rows": [
      {"id": 1, "event_time": "2026-01-02T00:00:00", "amount": 10},
      {"id": 2, "event_time": "2026-01-01T00:00:00", "amount": 20}
    ]},
    {"name": "replay", "clock": "2026-01-04T00:00:00", "rows": [
      {"id": 1, "event_time": "2026-01-02T00:00:00", "amount": 10},
      {"id": 2, "event_time": "2026-01-01T00:00:00", "amount": 20}
    ]}
  ]
}
```

比較には `EXCEPT ALL` を使い、重複行の個数まで含めて両側を突き合わせる。差が出たら最初の step で止め、どちらの側にだけある行かを最大 101 行まで保存する。

## わざと壊したモデルで差が出るか

検出できるかを確かめるため、増分の条件をわざと誤ったモデルを 2 つ用意した。1 つ目は、既存テーブルの最大 `event_time` より新しい行だけを取り込むモデルだ。

```sql
select id, event_time, amount
from {{ ref('events') }}
{% if is_incremental() %}
where event_time > (select max(event_time) from {{ this }})
{% endif %}
```

上のシナリオで流すと、`late_arrival` の step で差が出た。全件再計算の側にだけ `{"id":2,"event_time":"2026-01-01T00:00:00.000Z","amount":20}` があり、増分側では id=2 が欠落していた。

修正例では、時計から 3 日前までの行を毎回読み直す。

```sql
where event_time >= cast('{{ var("check_clock") }}' as timestamp) - interval 3 days
```

修正モデルは初回・遅延到着・再実行の 3 step で全件再計算と一致した。ただし 3 日を超えて遅れる行は救えない。一致はこのシナリオの範囲の結果だ。

2 つ目は、増分実行のたびに既存テーブルの合計を足し込むモデルで、同じ入力の再実行に弱い。初回と再実行の 2 step で流すと、増分側に `{"id":1,"amount":20}`、全件再計算の側に `{"id":1,"amount":10}` が残った。amount=10 が二重に加算されている。こちらも修正モデルでは 2 step とも一致した。

この実機検証では計 30 回の dbt 実行がすべて成功した。検証用に作った schema 14 個は削除し、schema 一覧に残っていないことも確認した。

## 反例を小さくして回帰シナリオにする

差が出たシナリオは、そのまま回帰テストとして保存したい。ただし入力が大きいと、どの行とどの step が原因なのかを読み取りにくい。そこで `--shrink-checks` を指定すると、step と行を削っては再実行する縮小を付けた。

縮小の規則は 3 つに絞った。初回の step は残す。元と同じ step で差が再現する候補だけを採用する。接続や実行のエラーで終わった候補は、反例として扱わない。

遅延到着の不具合モデルでは、2 回の追加の実行で 3 step から 2 step に縮んだ。`replay` の step が消え、`initial` と `late_arrival` だけが残った。保存したシナリオを CLI に渡すと、同じ `late_arrival` の step で id=2 の欠落が再現した。

縮小で得たのは削除を試した範囲での小さな反例で、大域的に最小とは限らない。追加の実行には warehouse の費用がかかるので、既定の試行回数は 0 にしている。

## 作るときにやめたこと

ローカルの SQLite で同じ比較を回す案もあった。しかし SQLite での成功は、Delta の MERGE と Databricks の SQL での成功の証拠にならない。ローカルのテストは入力の制約、比較、縮小、後片付けの境界の検証に使い、実機の結果とは別の証拠として保存した。

結果を unit test の YAML に書き出す案も見送った。上で触れたとおり、MERGE 後の最終状態を同じ形で表せないからだ。再実行できるシナリオの JSON とモデルの SQL を一次成果物にした。

実行のたびに結果が変わる SQL は、比較そのものが成り立たない。乱数や現在時刻の関数に加え、`TABLESAMPLE` や `first` / `last` / `any_value` も初版では受け付けない。順序を固定すれば安定する使い方もあるが、見分ける仕組みを入れるまでは保守的に拒否する。

後片付けにも判断が要った。検証用の schema は実行ごとにランダムな ID 付きの名前で作り、所有マーカーのコメントを付ける。削除するのは、作成を確認できてマーカーも一致する schema だけだ。作成や削除がタイムアウトして結果が分からない操作は、再試行せずに記録して schema を残す。縮小の途中でこの状態になったら探索を止め、直前に確認できた反例を保存して終える。

## まだ確かめていないこと

レビューで受けた指摘を直したあと、利用者が呼ぶ CLI の経路で、縮小を実機で再確認しようとした。ところが最初の dbt 実行で metastore のテーブル数の上限に当たり、確認できなかった。作った schema 2 個は削除済みだ。2026-10-02 の縮小の実機結果はライブラリを直接呼んだもので、修正後の CLI 経路の証拠には使っていない。上限の問題が解消したあとに、同じシナリオで縮小と保存ケースの再実行を確かめる必要がある。
