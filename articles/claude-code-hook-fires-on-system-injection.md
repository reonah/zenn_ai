Claude Code の UserPromptSubmit hook で、「ちがう」「そうじゃなく」のような後追いの訂正だけを JSONL に抜き出して貯めている。週 2 回の監査ループがそれを読み、同種の訂正が 2 回以上出ていればルールや skill に落とす、という運用だ。

先月その correction-log を開いたら、7 行のうち 4 行が自分の発話ではなかった。

## 記録されていたもの

4 行はすべて 2026-08-23 の 12:58 から 13:02 に連続して入っていて、一致した言い回し (`matched`) はどれも `ではなく` だった。中身は「Docker ではなく Databricks で検証した」という趣旨の、サブエージェントの作業要約である。

UserPromptSubmit はユーザがプロンプトを送ったときにだけ発火すると思い込んでいた。実際には `<task-notification>` や `<system-reminder>` のようなシステム注入の疑似プロンプトでも発火する。サブエージェントが仕事を終えて要約を返してくると、その本文が hook の入力の `.prompt` に入ってくる。訂正の言い回しは日本語の作業報告と語彙が重なるので、素直に一致してしまう。

## 実害は 2 つあった

1 つは監査の判定が歪むこと。訂正シグナルにノイズが混ざると、同種の訂正が 2 回以上という閾値の意味が壊れる。同じ `ではなく` が 4 件並んでいれば、監査は存在しない繰り返しを見つける。

もう 1 つは無人実行のほうに出た。この環境では correction-log の行数増分 (既定 3 行) をイベントにして、監査ループを launchd から起動している。4 分間で 4 行増えたので閾値を超え、無人の run が 1 回、空振りで走った。記録するだけで副作用のない hook のつもりだったが、ログの行数がスケジューラの入力になっている以上、誤検知はそのまま無人実行のコストになる。

## 先頭一致で落とす

スラッシュコマンドを除外している既存の分岐の直後、パターン照合よりも前に、先頭が既知のシステムタグで始まる入力を落とす分岐を足した。

```bash
# システム注入の疑似プロンプトは対象外 (ユーザの発話ではない)。先頭のタグだけで判定し、
# ユーザが本文中に貼った XML/HTML は落とさない
case "${PROMPT#"${PROMPT%%[![:space:]]*}"}" in
  '<task-notification>'* | '<system-reminder>'* | '<local-command-stdout>'* | \
  '<command-message>'* | '<command-name>'* | '<user-prompt-submit-hook>'*) exit 0 ;;
esac
```

判定を先頭一致に限ったのには理由がある。タグを含む行を位置によらず落とすと、「correction-log の `<task-notification>` の扱いが違う」のような正当な訂正まで消えてしまう。この調査自体がまさにそういう質問から始まった。パラメータ展開が二重に入っているのは、先頭の空白を剥がしてから判定するためだ。

hook のテストにはシステム注入 3 種と、先頭一致ではない位置にタグを含む正例を足した。修正後の記録は 0 件になった。

過去の 4 行は消していない。ログは追記専用で、その時点の監査が読んだ記録でもあるし、行数を減らすとイベント駆動側の基準線とも食い違う。修正は今後の記録にだけ効かせた。

## 人が書いていない入力はもう 1 種類あった

同じ観点で見直すと、貼り付けも引っかかっていた。X の投稿や記事の本文をそのまま貼ったプロンプトが「しないで」「ではなく」に一致して記録されていた例が、2026-08-30 に 2 件ある。

こちらは文字数で切ると、URL 付きの長い 1 行の訂正を落としてしまう。訂正は改行の少ない発話だという前提に賭けて、行数で判定することにした。既定は 6 行以上。

## prompt という名前を信用しない

hook の入力のキーが `prompt` だからといって、人が打った文字列とは限らない。UserPromptSubmit にパターン照合を書くなら、照合よりも前に「これは人の発話か」を判定する分岐を置いたほうがいい。ログをそのまま読む相手が人間なら誤検知はノイズで済むが、行数や件数が自動処理のトリガになっているなら、そこから先は勝手に動く。
