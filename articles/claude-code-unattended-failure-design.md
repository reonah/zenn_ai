Databricks のリリースノート確認、Obsidian に溜まったノートの整理、GitHub issue の消化。どれも Claude Code に頼めば数分で終わる作業だが、頼むのは毎回自分だった。要するにスケジューラが人間で、これが地味に嫌だった。

なので 2 か月前から、launchd (macOS のジョブスケジューラ) から Claude Code を headless モードで起動する無人ループを回している。今動いているのは 5 本。

- Databricks リリースノートの日次収集 (毎朝 07:30)
- Obsidian vault の整理と知識の昇格 (月・木 07:00)
- 計画承認済み GitHub issue の自動実装 (水 10:00)
- ハーネス自体の監査 (日・水 23:30)
- CLI 認証の生存点検 (毎朝 08:00。これだけ Claude を使わないただのシェル)

載せること自体は正直すぐ終わった。この 2 か月で手を入れ続けたのは実行部分ではなく、もっと地味なところだった。

## 最初に決めた 3 つ

設計として最初に決めたのは次の 3 つ。

- 完了判定は機械にやらせる。issue 対応ループならテストとリンターが exit 0 になったら完了で、モデルの「完了しました」は完了扱いにしない
- 作る側とマージする側を分ける。ループは PR を出すところで止めて、マージは人間が判断する
- 実行結果は Obsidian の daily note に集める。成功した日は要点だけ書いて黙る

3 つ目を一番徹底しているのが認証点検で、全 CLI の認証が生きている日はノートに何も書かない。失効を見つけた日だけ、再認証手順つきで書く。毎朝「全部正常です」と書いてくるノートなんて 3 日で読み飛ばすようになるのが目に見えているからだ。

で、実行自体は今日までそれほど崩れていない。やられたのは記録と監視の側で、2 回ある。

## 事件 1: CI はとっくに終わっていた

8 月頭、あるリポジトリの PR で CI の完了待ちをさせていたときの話。Claude は while + sleep で `gh pr checks --json` を叩き続ける自作ポーリングをバックグラウンドに投入した。CI は 26 秒で pass した。ポーリングはその後も延々と回り続けていた。

掘ると原因は 3 つ重なっていた。この Mac の gh が古くて、そもそも `--json` フラグが存在しない。なのに条件コマンドの stderr を `2>/dev/null` で捨てていたので、毎回のコマンド失敗がただの空出力になる。そして空出力は「まだ完了していない」と区別がつかない。結局止めたのは人間で、「これ CI もう終わってない？」と聞いてようやく発覚した。

腹立たしいのは、投入前にコマンドを一度素で実行してさえいれば `unknown flag: --json` が出て即死していたことだ。以後、完了待ちのやり方は常時ルールに落とした。

1. ツール付属の watch コマンド (`gh pr checks --watch` など) を第一候補にする
2. 自作ポーリングを書くなら、投入前に条件コマンド単体を 1 回実行して出力を見る
3. stderr を捨てない。条件が偽なのとコマンドが失敗しているのは別物で、失敗ならその場でループを終了させる
4. 上限時間を置く。失敗もキャンセルも終了条件に入れる (完了 = 成功ではない)

## 事件 2: ループは 57 ミリ秒で死んでいた

もう 1 つは無人ループ本体で起きた。8 月 10 日 09:00、vault 整理ループが起動 57 ミリ秒で落ちた。Claude Code の OAuth セッション失効が原因なので、落ちたこと自体は仕方がない。まずいのはここからで、私がそれに気づいたのは 6 日後だった。しかも通知や記録からではなく、「そういえば最近 loop が動いてなくない？」と自分で言い出して掘った結果として、である。

daily note に記録は残っていた。ただ「claude が異常終了した (ログ: ...err)」とだけ書かれていて、開いたその .err ファイルは 0 バイト。原因の OAuth 失効は結果 JSON の中に書いてあったのに、ノートからそこへたどる線がなかった。

さらに掘ると罠がもう 1 枚あった。claude は認証失効のとき、exit code 0 のまま結果 JSON の `is_error: true` だけで失敗を伝えてくることがある。exit code しか見ていなかった記録処理は、これを成功側に分類する。おまけに毎朝の認証点検は gcloud を「未インストール」としてスキップし続けていた。gcloud が mise 管理で、特定リポジトリの中でしか PATH に入らなかったせいだ。この間、私は 8 日で 6 回 `gcloud auth application-default login` を手で叩いている。点検ループは毎朝正常終了していて、点検すべきものが視界に入っていなかった。

対策として記録の側を作り直した。exit code と `is_error` の両方を見る判定ヘルパを共通化して、失敗した日は原因 1 行 (結果 JSON の `.result`、なければ `.subtype`、なければ stderr の最終行) と結果 JSON のパスを必ずノートに載せる。ヘルパにはテストも付けた。派手さのかけらもない変更だが、この 2 か月で一番効いた変更を挙げろと言われたらこれになる。

## ハーネス自体も監査対象にする

5 本のうち 1 本だけ毛色が違うので触れておく。週 2 回、Claude が自分の利用履歴を読む監査ループだ。プロンプト履歴、skill の起動ログ (どの skill が実際に使われたか)、訂正ログ (「ちがう」「やめて」で始まる後追い指示を hook で拾ったもの) を突き合わせて、よく頼まれるのに毎回口頭で説明している作業を skill 候補に、実態と乖離した資材を削除候補に挙げ、dotfiles への PR として提案してくる。

過去の自分の提案がどうなったかを振り返る工程も入れてある。却下された PR と同種の提案は再提出しない。マージされたのに 2 週間起動されない skill は削除候補に回す。ちなみに事件 2 の「失敗が見えない」問題を最初に見つけてきたのは、この監査ループだった。

## ループ本体より先に作るもの

スケジューラを人間から launchd に移すこと自体は 1 日仕事だった。難しかったのは、無人で動いているものが死んだときに死んだと分かるようにしておくほうで、ここは今も手を入れている。対話セッションなら失敗はその場で目に入る。無人ループの失敗は、記録の設計を間違えると 6 日間誰の視界にも入らない。

これからやる人に 1 つだけ挙げるなら、最初に作るべきはループ本体ではなくて、失敗した日にその原因が 1 行で目に入る記録の仕組みだと思う。うちは daily note に集めているが、Slack 通知でもメールでもいい。実行の自動化はモデルがやってくれる。残るのは、失敗を見えるようにしておく側の仕事だった。
