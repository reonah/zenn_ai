毎朝やっていたことがある。Databricks のリリースノートを開いて新着を確認する。Obsidian の vault にたまった未整理ノートを眺めて見なかったことにする。GitHub の issue を眺めて、今日やるものを選ぶ。どれも Claude Code に頼めば数分で終わる。ただし「頼めば」だ。頼むのは毎回自分で、つまりスケジューラが人間だった。

そこで 2 か月前から、launchd (macOS のジョブスケジューラ) から Claude Code を headless モードで起動する無人ループを運用している。現在動いているのは 5 本ある。

- Databricks リリースノートの日次収集 (毎朝 07:30)
- Obsidian vault の整理と知識の昇格 (月・木 07:00)
- 計画承認済み GitHub issue の自動実装 (水 10:00)
- ハーネス自体の監査 (日・水 23:30)
- CLI 認証の生存点検 (毎朝 08:00、これだけは Claude を使わないただのシェル)

始める前の想定はこうだった。cron 相当に載せてしまえば、あとは毎朝結果を読むだけになる。実際に 2 か月運用した今、いちばん手を入れたのは実行部分ではない。この記事は「放り込めば終わりなのか」という問いに、踏んだ失敗 2 つで答えるものだ。

## 設計原則: 完了は機械が判定し、マージは人間がする

無人ループの設計で最初に決めたのは次の 3 点だった。

- 完了判定は機械検証にする。issue 対応ループなら「テストとリンターが exit 0」で、モデルの自己申告 (「完了しました」) は完了扱いにしない
- Maker-Checker を分離する。作る側 (ループ) は PR を提案するまでで止め、マージ判断は人間に残す
- 実行結果は Obsidian の daily note に一元記録する。成功した日は静かに、書くのは要点だけ

3 点目の「静かに」は、認証点検ループで徹底している。全 CLI の認証が生きている日はノートに何も書かず、失効を見つけた日だけ再認証手順つきで書く。毎朝「全部正常です」と書かれるノートは、3 日で読まれなくなるからだ。

ここまでは順調に聞こえる。実際、実行そのものは順調だった。問題は別の場所で 2 回起きた。

## 事件 1: CI はとっくに終わっていた

8 月頭、あるリポジトリの PR で CI の完了を待たせていたときのことだ。Claude は自作のポーリングループ (while + sleep で `gh pr checks --json` を叩き続ける) をバックグラウンドに投入した。CI は 26 秒で pass した。ループは、その後も走り続けた。

原因は 3 つ重なっている。この Mac の gh が旧バージョンで `--json` フラグが存在しなかったこと。条件コマンドの stderr を `2>/dev/null` で捨てていたこと。その結果、「コマンドが毎回失敗して空出力」が「まだ完了していない」と区別できなかったことだ。発覚したのは、人間が「CI 終わっていませんか？」と聞いたときだった。

このループは投入前にコマンドを一度素で実行していれば、`unknown flag: --json` がその場で見えていた。以後、完了待ちは常時ルールとして 4 点に落とした。

1. ツール付属の watch コマンド (`gh pr checks --watch` 等) を第一候補にする
2. 自作ポーリングは投入前に条件コマンド単体を 1 回実行し、期待する出力を確認する
3. stderr を捨てず、「条件が偽」と「コマンドが失敗」を区別してループを終了させる
4. 上限時間を置き、失敗・キャンセルも終了条件に含める

2 番目が、まさにこの事件の原因そのものだ。

## 事件 2: ループは 57 ミリ秒で死んでいた

もう一つは無人ループ本体で起きた。8 月 10 日 09:00、vault 整理ループが起動 57 ミリ秒で失敗した。Claude Code の OAuth セッションが失効していたためだ。ここまでは仕方がない。問題はその後で、私がそれに気づいたのは 6 日後、「そういえば loop が機能していない気がする」と自分で言い出したときだった。

daily note には記録が残っていた。ただしこう書かれていた。「claude が異常終了した (ログ: ...err)」。そしてその .err ファイルは 0 バイトだった。原因 (OAuth 失効) は結果 JSON の中にあったのに、ノートは誰もそこを指していなかった。

掘ってみると、罠は二重だった。claude は認証失効を exit code 0 のまま、結果 JSON の `is_error: true` で返すことがある。exit code だけを見ていた記録処理は、これを失敗と判定できない。さらに同じ時期、毎朝の認証点検は gcloud を「未インストール」としてスキップし続けていた。gcloud が mise 管理で、特定リポジトリの中でしか PATH に入らなかったためだ。その間、私は 8 日間で 6 回、手で `gcloud auth application-default login` を叩いていた。点検ループは毎朝正常終了していて、点検すべき対象が見えていなかった。

対策は「失敗の記録」を仕組みに変えることだった。exit code と `is_error` の両方を見る判定ヘルパを作り、失敗時は原因 1 行 (結果 JSON の `.result`、なければ `.subtype`、なければ stderr 最終行) と結果 JSON のパスを必ずノートに載せる。全ループの記録分岐をこのヘルパに統一し、テストも付けた。

## ハーネス自体も監査対象にする

5 本のうち 1 本は毛色が違う。週 2 回、Claude が自分の利用履歴を読む監査ループだ。ユーザのプロンプト履歴、skill の起動ログ (どの skill が実際に使われたか)、訂正ログ (「ちがう」「やめて」で始まる後追い指示の記録) を突き合わせ、「よく頼まれるのに毎回説明している作業」を skill 候補として、「実態と乖離した資材」を削除候補として、dotfiles への PR で提案する。

このループには過去の自分の提案の結末を振り返る工程がある。却下された PR と同種の提案は再提出しない。マージされたのに 2 週間起動されない skill は削除候補に回す。事件 2 の「失敗が見えない問題」を見つけたのも、実はこの監査ループだった。

## 放り込めば終わり、ではなかった

冒頭の問いに戻る。スケジューラを人間から launchd に移すこと自体は、正直なところ簡単だった。2 か月で分かったのは、無人運転の本丸は「動くこと」ではなく「死んだと分かること」の側にある、ということだ。対話セッションなら失敗はその場で目に入る。無人ループの失敗は、記録の設計を間違えると 6 日間誰にも見えない。

これから同じことをやる人に一つだけ挙げるなら、最初に作るべきはループ本体ではなく、失敗した日にその原因が必ず 1 行で目に入る記録の仕組みだ。私の場合それは daily note だったが、Slack 通知でもメールでもいい。実行の自動化はモデルがやってくれる。失敗の設計は、まだ人間の仕事だった。
