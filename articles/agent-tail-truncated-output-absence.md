コーディングエージェントに Databricks の作業を任せていたら、Job 実行の成果物フォルダが Volume に「残っていない」と報告された。実際にはフォルダは存在した。根拠にされたのは、別の目的で `| tail -3` を付けて絞った一覧だった。

## 何が起きたか

2026-10-28 の作業である。Volume には Job の実行 ID を名前にしたフォルダが並ぶ。エージェントは最新のフォルダ名を取り出すために、次の形のコマンドを実行していた (パスは伏せた)。

```bash
databricks fs ls <Volume のパス> | tail -3
```

`tail` は新しい方の数件を見るために付けたものだ。その後、Job の実行履歴を読んで特定の実行の成果物に触れる段になり、エージェントはこの 3 行の出力を不在の根拠に流用した。対象の ID が 3 行の中に無いことから、フォルダは無いと結論したわけだ。出力が末尾 3 件に切り詰められていた事情は、報告の時点で抜け落ちていた。

## 短い問題文では再現しなかった

再発防止として最初に考えたのは、常時読み込むルールに「切り詰めた出力から不在・件数を結論しない」と 1 行足す案だった。足す前に、変更前の状態で `claude -p` に 4 問を解かせた。ツールの使用は禁止し、実行記録だけを渡して報告文を書かせる形式である。

| 問い | 内容 | 結果 |
| --- | --- | --- |
| A | 末尾 3 行の一覧だけを示し、対象の有無を問う | 2/2 合格。判断できないと回答 |
| A2 | 別目的の `tail` を、後で不在の根拠に流用する状況を再現 | 有効回答 2/2 合格。別の 1 回は空の出力で、実行環境の失敗 |
| B | 絞らない全件の一覧で有無を問う (安全な反例) | 2/2 で「一覧にない」と回答 |
| C | テスト結果の末尾の要約行を `tail` で見る (無関係な作業) | 2/2 で成功と回答 |

変更前の版が全問に合格したので、ルール文を足しても改善を示せない。そこでルールの追加は見送った。実際の誤りは長い作業の途中で起きており、短い問題文に切り出すと、モデルは切り詰めに気づいた。過去の訂正を記録したログ (21 行) にも同種の訂正は無く、別の作業で繰り返している証拠も無かった。

## 対策: 出力がちょうど N 行のときだけ注意を添える

2026-10-29、ルール文ではなく Claude Code の PostToolUse hook で対処することにした。Bash の実行後に次の 2 条件を両方満たしたときだけ、追加の文脈をモデルに渡す。

* コマンドの最後の段が `| head -N` か `| tail -N` である
* stdout がちょうど N 行である

出力が N 行未満なら全件が出ているので、何も言わない。判定の中心は次の部分だ。

```bash
LAST_STAGE='\|[[:space:]]*(head|tail)(([[:space:]]+(-n[[:space:]]*|--lines=|-)[0-9]+)?)$'
MATCH=$(printf '%s' "$CMD" | grep -oE "$LAST_STAGE" | tail -1)
[ -n "$MATCH" ] || exit 0

N=$(printf '%s' "$MATCH" | grep -oE '[0-9]+$' || true)
# 行数を省くと head・tail とも 10 行
[ -n "$N" ] || N=10

LINES=$(printf '%s' "$STDOUT" | awk 'END { print NR }')
[ "$LINES" = "$N" ] || exit 0
```

条件に当たると、`additionalContext` に「続きがあった可能性がある」「この出力だけで『ない』『N 件だけ』と結論しない」「報告前に絞らずに実行するか、grep や wc -l で対象を直接確かめる」の 3 点を入れて返す。

対象を最後の段に限ったのは、途中の段で絞ると後段で行数が変わるからだ。`ls | head -3 | wc -l` の出力は 1 行で、N との比較が切り詰めの有無を示さない。`tail -n +2` (2 行目以降) と `head -c` (バイト数) も対象から外した。テストは正例 7 件と負例 8 件で、15 件すべて通っている。

## 効果はまだ測れていない

この hook で誤報告が減ったかは未検証である。長い会話の途中で同じ状況を再現できていないからだ。注意が出る頻度と、それで文脈がどれだけ増えるかも測っていない。

いま確かめられているのは 2 点に留まる。短い問題文の評価ではこの失敗を捕まえられなかったこと、そして hook の判定が 15 件のテストどおりに動くことである。
